# Фоновая работа логирования через планировщик задач

## Проблема

Сейчас автозапуск Ven4Control — запись в `HKCU\...\Run` (`autostart.py`). Она
срабатывает только при входе конкретного пользователя в систему и не переживает
перезагрузку без входа: если компьютер перезагрузился ночью (например, из-за
обновлений) и никто не вошёл в систему, фоновое логирование не поднимется, и
реальный обрыв интернета в этот период останется незамеченным — а именно для
поимки таких обрывов логирование и существует.

Полноценная Windows-служба была рассмотрена и отклонена: нужны права
администратора на установку, служба работает в Session 0 (нет трея — весь
смысл приложения как трей-инструмента теряется) и не видит Credential Manager
текущего пользователя (SSH-ключи/пароли insertions привязаны к профилю).

## Решение

Задача в планировщике Windows с триггером «At startup» и параметром «Run
whether user is logged on or not» — **опция сверх** существующего
HKCU-автозапуска, не замена. Регистрация задачи требует одного UAC-подтверждения
на кнопку «включить», дальнейшие запуски (при каждой загрузке системы) элевации
не требуют.

### Почему не Windows-служба, но структурно похожая проблема

Задача с «Run whether user is logged on or not» до входа пользователя тоже
работает в непривычной, не полностью интерактивной сессии (нет трея, экрана
никто не видит — это ожидаемо, там некому смотреть на иконку). Но после
реального входа пользователя эта уже запущенная задача **не переезжает** в его
интерактивную сессию сама — а параллельно сработает существующий
HKCU-автозапуск и поднимет ВТОРОЙ процесс с треем. Оба процесса независимо
откроют SSH-сессии логирования к одним и тем же устройствам (реальным роутерам
и серверам пользователя) — данные это не испортит (каждая сессия пишет в свою
папку с меткой времени), но подключения задвоятся, а в трее окажется два
значка вместо одного.

Отсюда — второй компонент этой фичи, без которого первый вреден:
**защита от повторного запуска процесса**.

## Компоненты

### 1. `scheduled_task.py` (новый модуль, рядом с `autostart.py`)

Тот же стиль API: `is_supported()`, `is_enabled()`, `enable()`, `disable()`.
Реализация — вызов `powershell.exe`, без pywin32/COM.

- Имя задачи: `Ven4Control-Background`.
- Действие — команда из уже существующего `autostart.startup_command()`
  (тот же `--tray`, никакой второй копии этой логики).
- Триггер: `New-ScheduledTaskTrigger -AtStartup`.
- Принципал: `New-ScheduledTaskPrincipal -UserId "<текущий пользователь>"
  -LogonType S4U -RunLevel Limited`. S4U выбран вместо хранимого пароля:
  ничего не хранится и не протухает при смене пароля входа, при этом профиль
  пользователя всё равно загружается — Credential Manager с SSH-ключами
  доступен.
- Настройки: `New-ScheduledTaskSettingsSet -AllowStartIfOnBatteries
  -DontStopIfGoingOnBatteries -StartWhenAvailable` (ноутбук может быть
  выключен физически в момент штатного времени запуска — задача должна
  наверстать при следующей возможности, а не потеряться).
- `enable()`/`disable()` регистрируют/удаляют задачу через один и тот же
  повышенный вызов PowerShell (`ShellExecuteW` с verb `runas`, команда —
  `-EncodedCommand` с base64/UTF-16LE, чтобы не собирать кавычки вручную).
  Отказ пользователя от UAC или ошибка PowerShell — пробрасывается наверх как
  исключение (аналог `OSError` у `autostart.enable/disable`).
- `is_enabled()` — обычный неэлевированный `Get-ScheduledTask -TaskName ...
  -ErrorAction SilentlyContinue`, элевации не требует.

### 2. `single_instance.py` (новый модуль)

- `QLocalServer`/`QLocalSocket`, фиксированное имя сервера
  (`Ven4Control-instance`).
- `SingleInstanceGuard.try_acquire() -> bool`: пробует подключиться к уже
  существующему серверу с коротким таймаутом; если получилось — этот процесс
  не главный, возвращает `False`. Если нет — сам поднимает сервер
  (`QLocalServer.removeServer()` перед `listen()`, чтобы не мешал огрызок
  сокета от аварийного завершения) и становится главным (`True`).
- `notify_show()` — короткое сообщение главному процессу «покажи трей» (для
  процесса, который проиграл гонку за `try_acquire`).
- Главный процесс подключает `newConnection` к обработчику, который читает
  сообщение и эмитит сигнал `show_requested`.

### 3. Интеграция в `app.py`

- `main()`: `QApplication` создаётся первым (нужен для `QLocalSocket`), сразу
  за ним — проверка guard'а. Если процесс проиграл гонку — `notify_show()` и
  немедленный выход (return 0), **до** создания `MainWindow` (значит без
  повторного открытия БД устройств и SSH-сессий). Если процесс главный — как
  сейчас, плюс `guard.show_requested.connect(window.show_from_tray)`.
- Трей-меню: второй чекбоксный пункт «Работать в фоне до входа в систему»,
  сразу под «Запускать при входе в Windows». Полностью независим от него — не
  включает и не выключает HKCU-автозапуск.
  - При включении: сначала `QMessageBox.information` с объяснением
    предстоящего однократного UAC-запроса, затем `scheduled_task.enable()`.
  - При ошибке (отказ от UAC, сбой PowerShell) — `QMessageBox.warning` и
    чекбокс возвращается в исходное состояние — тот же паттерн, что уже
    используется в `toggle_autostart` для реестра.
  - Начальное состояние чекбокса — `scheduled_task.is_enabled()`,
    `setEnabled(scheduled_task.is_supported())`.

## Данные и порядок выполнения

1. Пользователь включает опцию в трее → предупреждение → UAC → задача
   зарегистрирована.
2. При следующей перезагрузке: задача стартует до входа пользователя,
   поднимает главный процесс без окна, `restore_background_sessions()`
   (существующий код, уже не завязан на наличие трея) поднимает сессии для
   устройств с `log_background=True`.
3. Пользователь входит в систему: HKCU-автозапуск стартует второй процесс →
   тот проигрывает гонку за guard → шлёт «покажи трей» первому → выходит.
   Пользователь видит ровно один трей-значок, ровно один набор SSH-сессий.
4. Выключение опции удаляет задачу планировщика, но не трогает уже запущенный
   процесс — тот продолжает работать до следующей перезагрузки/выхода.

## Обработка ошибок

- Любая ошибка регистрации/удаления задачи (отказ UAC, PowerShell не найден,
  ненулевой код возврата) — не должна портить существующий HKCU-автозапуск и
  не должна ронять приложение; сообщается пользователю текстом ошибки.
- Guard: если `QLocalServer.listen()` не удаётся по причине, отличной от
  «сервер уже существует» (например, редкая проблема с правами на именованный
  канал) — процесс не должен упасть; ведёт себя как единственный (не блокирует
  запуск), деградация до состояния «без защиты от дублирования» лучше отказа
  запуститься.

## Тестирование

- `tests/test_scheduled_task.py` — как `tests/test_autostart.py`: юниты с
  подменой `subprocess.run`/`Popen` (корректность собранных аргументов
  PowerShell, разбор состояния `is_enabled`, проброс ошибки при ненулевом
  коде возврата). Реальную регистрацию с S4U и живой UAC юнит-тестом не
  проверить.
- `tests/test_single_instance.py` — два guard'а на тестовое имя сервера
  (не боевое `Ven4Control-instance`, чтобы не пересечься с реально запущенным
  приложением): второй должен получить `False`, `notify_show()` у второго
  должен вызвать сигнал у первого.
- **Обязательная живая проверка на реальном устройстве перед мержем** (тот же
  принцип, что уже применялся для SSH/RDP-туннеля):
  1. Включить опцию → один UAC → `Get-ScheduledTask -TaskName
     Ven4Control-Background` подтверждает регистрацию, триггер и принципал.
  2. Перезагрузка без немедленного входа (или контроль через другую сессию/
     RDP) → процесс уже в `Get-Process` headless, для устройства с
     `log_background=True` появилась новая папка сессии.
  3. Вход в систему → ровно один процесс Ven4Control, трей появился, в логах
     обеих сторон (клиент + сам роутер/сервер, если есть журнал подключений)
     нет второго одновременного SSH-подключения.
  4. Выключение опции → `Get-ScheduledTask` больше не находит задачу,
     уже запущенный процесс продолжает работать как ни в чём не бывало.

## Вне рамок

- **`devices.db` эта фича не трогает вообще** — ни схему, ни запись, ни
  чтение устройств. Затрагиваются только реестр планировщика Windows
  (задача `Ven4Control-Background`) и локальный IPC между процессами
  приложения. Правило «не потерять реальную базу устройств» здесь не в
  зоне риска — оно относится к отдельной задаче (сверка/починка fingerprint
  через `DeviceStorage.save()`), не к этой.
- Судьба HKCU-автозапуска не меняется — обе опции остаются независимыми.
- Полноценная Windows-служба — отклонена, см. «Решение» выше.
- Поведение на других ОС не рассматривается: `is_supported()` как и в
  `autostart.py` возвращает `False` вне Windows, опция скрыта/неактивна.
