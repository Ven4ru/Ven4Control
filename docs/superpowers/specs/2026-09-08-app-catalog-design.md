# Установка приложений на устройство

## Проблема

У `DeviceControlDialog` нет способа установить пакет на устройство —
только «Обновить пакеты» (апгрейд уже установленного целиком,
`remote_control.update_packages`). Мотивирующий кейс: на роутере Ишим
нет `openssh-sftp-server` (dropbear его не тянет по умолчанию), и
единственный способ починить SFTP там сегодня — руками через встроенный
терминал. Нужна страница поиска и установки пакетов из уже
настроенных на устройстве репозиториев (не свой каталог Ven4Control —
именно то, что уже видит `opkg`/`apk`/`apt` на конкретном устройстве).

## Решение

Новая страница «Приложения» в сайдбар-навигации `DeviceControlDialog`
(седьмой пункт, тем же способом, что и остальные шесть). Поиск —
команда по SSH через тот же принцип, что уже разделяет `update_packages`
по платформе (`apk`/`opkg`/`apt-get`), плюс `winget` для Windows и кнопка
Ven4Tools — вынесены в отдельную будущую фазу 2, не в этом плане.

## Команды — проверены живьём, не по памяти

**apk** (проверено на `192.168.1.1` и `100.112.90.88`, оба реальных
роутера сейчас на apk, не opkg):
```sh
apk update >/dev/null 2>&1
apk search -q -d "$TERM" 2>/dev/null
```
`-q` (quiet) даёt чистое имя пакета без версии на строку — критично:
`apk add` с версионным суффиксом (`openssh-sftp-server-10.3_p1-r1`,
именно так выглядит вывод БЕЗ `-q`) падает с «no such package», нужно
чистое `openssh-sftp-server`. `-d` — поиск и по описанию тоже, не
только по имени (подтверждено: `sftp` находит `lftp`, `sshfs` через
описание, не только пакеты с «sftp» в названии). Установка:
```sh
apk add "$NAME"
```
(проверено симуляцией `apk add --simulate openssh-sftp-server` —
корректно разрешается, ничего не ломает; реальная установка не
делалась намеренно, чтобы не трогать боевой роутер без необходимости).

**opkg** (НЕ проверено живьём — ни одно реальное устройство пользователя
сейчас не использует opkg, обе прошивки уже на apk; команда написана по
аналогии с уже работающим веткой `update_packages` для этой же
платформы, но нуждается в верификации при первой встрече с реальным
opkg-устройством):
```sh
opkg update >/dev/null 2>&1
opkg list 2>/dev/null | grep -i "$TERM"
```
Формат строки `opkg list`: `<имя> - <версия> - <описание>` — парсинг:
взять текст до первого ` - `.
```sh
opkg install "$NAME"
```

**apt** (проверено на VPS `138.16.152.133`, Ubuntu 24.04):
```sh
sudo -n apt-get update >/dev/null 2>&1
apt-cache search "$TERM"
```
Формат строки: `<имя> - <описание>` — тот же простой парсинг, что у
opkg. Установка (тот же sudo-паттерн, что уже в `update_packages`):
```sh
sudo -n env DEBIAN_FRONTEND=noninteractive apt-get install -y "$NAME"
```

## UI

Страница «Приложения»: строка поиска + кнопка «Найти» → таблица
результатов (Имя / Описание) → выбор строки → кнопка «Установить» →
область вывода команды (тот же паттерн, что уже на странице
«Обслуживание» — `QTextEdit` с результатом операции). Подтверждение
перед установкой НЕ нужно — это не разрушительное действие (в отличие
от перезагрузки/прошивки, у которых confirm уже есть).

## Фаза 2 — Windows (`winget`) + кнопка «Ven4Tools»

Согласовано в брейнсторминге: только `winget` (встроен в Windows 10/11,
ничего доустанавливать не нужно; choco потребовал бы отдельный бутстрап
— не в этой задаче). Кнопка «Ven4Tools» — скачать ZIP с GitHub Releases,
распаковать в фиксированную папку (тот же путь и при первой установке, и
при обновлении — перезаписывает).

### `winget search` — проверено живьём на VenchWork (Windows 11, winget v1.29.290)

```powershell
winget search <термин> --accept-source-agreements
```
Вывод — таблица с выравниванием пробелами:
```
Name                   Id                              Version       Match            Source
---------------------------------------------------------------------------------------------
Avash                  AdrienCros.Avash                0.10.1        Tag: sftp        winget
Bitvise SSH Client     Bitvise.SSH.Client              9.66          Tag: sftp        winget
```
`winget` не даёт JSON/структурированный вывод для `search` (проверено —
`winget search --help` такого флага не предлагает). Парсинг — деление
строки по 2+ пробелам подряд (`re.split(r"\s{2,}", line)`): внутри
значения столбца пробел встречается не больше одного раза подряд
(`Bitvise SSH Client`, `Tag: sftp`) — граница столбца отличается
количеством пробелов, не их наличием. В установку идёт **Id**
(`Bitvise.SSH.Client`), не Name — тот же принцип, что и у apk/opkg/apt:
`PackageResult.name` = точный устанавливаемый идентификатор, не
«человеческое» название; Name+Version собираются в `description` для
отображения.

Установка (флаги подтверждены по `winget install --help` на реальной
машине):
```powershell
winget install --id <Id> --exact --silent --accept-package-agreements --accept-source-agreements
```
`--exact` — важно: без него `--id` мог бы матчиться нечётко и поставить
не тот пакет. `-h`/`--silent` — именно так называется флаг тихой
установки у winget (не `-s`, тот занят под `--source`).

### Кнопка «Ven4Tools» — GitHub API + скачивание + распаковка, проверено живьём на VenchWork

Ven4Tools распространяется ZIP-архивом с версией в имени файла
(`Ven4Tools-Client-5.1.1.zip`) — стабильной ссылки вида
`.../releases/latest/download/<фиксированное-имя>.zip` нет (имя меняется
от релиза к релизу). Нужен запрос к GitHub API за последним релизом:

```powershell
$url = (Invoke-RestMethod -Uri "https://api.github.com/repos/Ven4ru/Ven4Tools/releases/latest").assets |
    Where-Object { $_.name -like "*.zip" } |
    Select-Object -First 1 -ExpandProperty browser_download_url
```
Проверено вживую на VenchWork — возвращает реальный
`https://github.com/Ven4ru/Ven4Tools/releases/download/v5.1.1/Ven4Tools-Client-5.1.1.zip`.

Дальше — скачать во временный файл, распаковать в фиксированную папку
(предлагается `C:\Ven4Tools`), удалить временный ZIP:
```powershell
$zipPath = "$env:TEMP\ven4tools-update.zip"
Invoke-WebRequest -Uri $url -OutFile $zipPath
Expand-Archive -Path $zipPath -DestinationPath "C:\Ven4Tools" -Force
Remove-Item $zipPath -Force
```
**Решено при написании плана**: НЕ очищать `C:\Ven4Tools` перед
распаковкой — просто `Expand-Archive -Force` поверх существующей папки.
Причина: очистка — разрушительное действие без явного согласия
пользователя на конкретный клик (риск задеть что-то, что пользователь
сам туда положил, вопреки соглашению «эта папка принадлежит кнопке»,
которое реально нигде не показано и не подтверждено пользователем в UI).
Устаревшие файлы от предыдущей версии, которых больше нет в новом
архиве, могут задержаться — известное ограничение, не критично для
работающего приложения (мусорный файл, не сломанная функциональность).
Полная очистка — не отвергнута навсегда, просто отдельная возможная
доработка, если на практике всплывёт реальная проблема с висящими
файлами.

**Экранирование**: команды для Windows идут через PowerShell — экранирование
строк (поисковый термин, имя пакета) через `shlex.quote()` (POSIX-стиль,
уже используется для веток `apk`/`opkg`/`apt`) для PowerShell **неверно** —
PowerShell экранирует `'` внутри `'...'`-строки удвоением (`''`), не
обратным слэшем. Нужна отдельная функция под PowerShell-экранирование,
переиспользующая уже существующий `_quoted()` из `scheduled_task.py`
(там это уже реализовано верно и покрыто тестами для планировщика) —
вынести в общий модуль вместо дублирования во второй раз.

**Живая находка при подготовке плана**: `Invoke-WebRequest` без
`$ProgressPreference = "SilentlyContinue"` может зависать на
неинтерактивной SSH-сессии (нет реального терминала для прогресс-бара) —
обязательно включать эту строку перед любым `Invoke-WebRequest` в
командах установки. Отдельно от этого: скачивание большого файла (85.6
МБ) зависало на конкретной машине (`VenchWork`) даже с этой настройкой и
даже через голый `curl.exe` — при этом GitHub API и TCP-коннект к
`objects.githubusercontent.com:443` с той же машины отвечали нормально, и
тот же самый файл скачивался с домашнего ПК за 4 секунды. Это диагностировано
как особенность сетевого пути конкретной машины, не ошибка дизайна —
правильная реакция кода: щедрый таймаут (600с), не попытка обойти
медленную сеть каким-то технически изощрённым способом.

### UI

Тот же паттерн, что и у apk/opkg/apt — общая страница «Приложения» и
общая таблица результатов работают одинаково для Windows-устройств
(поиск через winget вместо apk/apt), без отдельной ветки UI. Кнопка
«Установить/обновить Ven4Tools» — отдельная кнопка на той же странице,
видна всегда (как и остальные maintenance-кнопки в проекте, которые
всегда видны независимо от платформы и просто дают понятную ошибку,
если платформа не подходит — тот же принцип, не городить отдельную
platform-conditional видимость ради одной кнопки).

## Установка по ссылке (не из репозитория) — отдельная будущая возможность

Не всё нужное есть в стандартных репозиториях `apk`/`opkg`/`apt`. Мотивирующие
примеры пользователя — реальные проекты, проверено по их собственным
README на GitHub, не с чужих слов:

- **podkop** (`itdoginfo/podkop`) — установка ОДНОЙ командой, которую сам
  проект публикует как официальный способ:
  ```sh
  sh <(wget -O - https://raw.githubusercontent.com/itdoginfo/podkop/refs/heads/main/install.sh)
  ```
  Скрипт сам добавляет нужный репозиторий, ставит пакет, ничего решать
  на стороне Ven4Control не нужно — просто выполнить URL целиком.

- **zapret-openwrt** (`remittor/zapret-openwrt`, управляется через
  `StressOzz/Zapret-Manager`) — устроено СЛОЖНЕЕ и принципиально иначе:
  релизы на GitHub — ZIP-архивы **по архитектуре устройства**
  (`zapret_v72.20260307_aarch64_cortex-a53.zip`,
  `..._arm_cortex-a7.zip` и т.д., проверено по факту в реальном списке
  релизов). Нет единого скрипта-установщика — нужно определить
  архитектуру устройства (`apk info -a` / `ubus call system board`),
  скачать подходящий ZIP, распаковать, установить пакет(ы) из архива
  локально (`apk add --allow-untrusted <файл>` / `opkg install <файл>`).
  Подбор архива автоматически — риск скачать не тот архитектурный
  вариант и получить нерабочий/несовместимый бинарник.

**Дизайн для будущей фазы (не проектировался детально, только направление)**:
UI-поле «Установить по ссылке» с двумя режимами по факту разной механики
выше — (а) выполнить скрипт-установщик по URL целиком (простой случай,
как podkop) и (б) скачать конкретный файл по прямой ссылке на нужный
пользователю архив/пакет и установить его локально (пользователь сам
подставляет ссылку на актуальную для своего устройства архитектуру —
не пытаемся угадывать автоматически, ошибка здесь дороже, чем при
установке из репозитория). **Обязательно нужно предупреждение/подтверждение
перед выполнением** — это не `apk add <имя_из_каталога>`, а исполнение
произвольного стороннего скрипта с правами root на устройстве
пользователя, риск принципиально другого порядка. Не планируется в
текущем плане (`docs/superpowers/plans/2026-09-08-app-catalog.md`) —
отдельная будущая задача, когда пользователь попросит спроектировать её
подробно.

## Явно вне рамок

- Индикатор «уже установлено» в результатах поиска — пользователь
  подтвердил: не нужно, список установленного уже доступен в
  «Обслуживание»/выводе команд.
- Множественный выбор для пакетной установки.
- Собственный курируемый каталог Ven4Control — используются только
  репозитории, уже настроенные на самом устройстве.
