# Установка приложений на устройство (фаза 1: OpenWrt/Ubuntu)

## Проблема

У `DeviceControlDialog` нет способа установить пакет на устройство —
только «Обновить пакеты» (апгрейд уже установленного целиком,
`remote_control.update_packages`). Мотивирующий кейс: на роутере Ишим
нет `openssh-sftp-server` (dropbear его не тянет по умолчанию), и
единственный способ починить SFTP там сегодня — руками через встроенный
терминал. Нужна страница поиска и установки пакетов из уже
настроенных на устройстве репозиториев (не свой каталог Ven4Control —
именно то, что уже видит `opkg`/`apk`/`apt` на конкретном устройстве).

## Решение

Новая страница «Приложения» в сайдбар-навигации `DeviceControlDialog`
(седьмой пункт, тем же способом, что и остальные шесть). Поиск —
команда по SSH через тот же принцип, что уже разделяет `update_packages`
по платформе (`apk`/`opkg`/`apt-get`), плюс `winget` для Windows и кнопка
Ven4Tools — вынесены в отдельную будущую фазу 2, не в этом плане.

## Команды — проверены живьём, не по памяти

**apk** (проверено на `192.168.1.1` и `100.112.90.88`, оба реальных
роутера сейчас на apk, не opkg):
```sh
apk update >/dev/null 2>&1
apk search -q -d "$TERM" 2>/dev/null
```
`-q` (quiet) даёt чистое имя пакета без версии на строку — критично:
`apk add` с версионным суффиксом (`openssh-sftp-server-10.3_p1-r1`,
именно так выглядит вывод БЕЗ `-q`) падает с «no such package», нужно
чистое `openssh-sftp-server`. `-d` — поиск и по описанию тоже, не
только по имени (подтверждено: `sftp` находит `lftp`, `sshfs` через
описание, не только пакеты с «sftp» в названии). Установка:
```sh
apk add "$NAME"
```
(проверено симуляцией `apk add --simulate openssh-sftp-server` —
корректно разрешается, ничего не ломает; реальная установка не
делалась намеренно, чтобы не трогать боевой роутер без необходимости).

**opkg** (НЕ проверено живьём — ни одно реальное устройство пользователя
сейчас не использует opkg, обе прошивки уже на apk; команда написана по
аналогии с уже работающим веткой `update_packages` для этой же
платформы, но нуждается в верификации при первой встрече с реальным
opkg-устройством):
```sh
opkg update >/dev/null 2>&1
opkg list 2>/dev/null | grep -i "$TERM"
```
Формат строки `opkg list`: `<имя> - <версия> - <описание>` — парсинг:
взять текст до первого ` - `.
```sh
opkg install "$NAME"
```

**apt** (проверено на VPS `138.16.152.133`, Ubuntu 24.04):
```sh
sudo -n apt-get update >/dev/null 2>&1
apt-cache search "$TERM"
```
Формат строки: `<имя> - <описание>` — тот же простой парсинг, что у
opkg. Установка (тот же sudo-паттерн, что уже в `update_packages`):
```sh
sudo -n env DEBIAN_FRONTEND=noninteractive apt-get install -y "$NAME"
```

## UI

Страница «Приложения»: строка поиска + кнопка «Найти» → таблица
результатов (Имя / Описание) → выбор строки → кнопка «Установить» →
область вывода команды (тот же паттерн, что уже на странице
«Обслуживание» — `QTextEdit` с результатом операции). Подтверждение
перед установкой НЕ нужно — это не разрушительное действие (в отличие
от перезагрузки/прошивки, у которых confirm уже есть).

## Установка по ссылке (не из репозитория) — отдельная будущая возможность

Не всё нужное есть в стандартных репозиториях `apk`/`opkg`/`apt`. Мотивирующие
примеры пользователя — реальные проекты, проверено по их собственным
README на GitHub, не с чужих слов:

- **podkop** (`itdoginfo/podkop`) — установка ОДНОЙ командой, которую сам
  проект публикует как официальный способ:
  ```sh
  sh <(wget -O - https://raw.githubusercontent.com/itdoginfo/podkop/refs/heads/main/install.sh)
  ```
  Скрипт сам добавляет нужный репозиторий, ставит пакет, ничего решать
  на стороне Ven4Control не нужно — просто выполнить URL целиком.

- **zapret-openwrt** (`remittor/zapret-openwrt`, управляется через
  `StressOzz/Zapret-Manager`) — устроено СЛОЖНЕЕ и принципиально иначе:
  релизы на GitHub — ZIP-архивы **по архитектуре устройства**
  (`zapret_v72.20260307_aarch64_cortex-a53.zip`,
  `..._arm_cortex-a7.zip` и т.д., проверено по факту в реальном списке
  релизов). Нет единого скрипта-установщика — нужно определить
  архитектуру устройства (`apk info -a` / `ubus call system board`),
  скачать подходящий ZIP, распаковать, установить пакет(ы) из архива
  локально (`apk add --allow-untrusted <файл>` / `opkg install <файл>`).
  Подбор архива автоматически — риск скачать не тот архитектурный
  вариант и получить нерабочий/несовместимый бинарник.

**Дизайн для будущей фазы (не проектировался детально, только направление)**:
UI-поле «Установить по ссылке» с двумя режимами по факту разной механики
выше — (а) выполнить скрипт-установщик по URL целиком (простой случай,
как podkop) и (б) скачать конкретный файл по прямой ссылке на нужный
пользователю архив/пакет и установить его локально (пользователь сам
подставляет ссылку на актуальную для своего устройства архитектуру —
не пытаемся угадывать автоматически, ошибка здесь дороже, чем при
установке из репозитория). **Обязательно нужно предупреждение/подтверждение
перед выполнением** — это не `apk add <имя_из_каталога>`, а исполнение
произвольного стороннего скрипта с правами root на устройстве
пользователя, риск принципиально другого порядка. Не планируется в
текущем плане (`docs/superpowers/plans/2026-09-08-app-catalog.md`) —
отдельная будущая задача, когда пользователь попросит спроектировать её
подробно.

## Явно вне рамок этой фазы

- Windows (`winget`) и кнопка «Ven4Tools» — отдельная будущая фаза,
  требует своего дизайна (GitHub API за последним релизом, скачивание,
  распаковка) — не планируется в этом документе.
- Индикатор «уже установлено» в результатах поиска — пользователь
  подтвердил: не нужно, список установленного уже доступен в
  «Обслуживание»/выводе команд.
- Множественный выбор для пакетной установки.
- Собственный курируемый каталог Ven4Control — используются только
  репозитории, уже настроенные на самом устройстве.

## Порядок реализации

Одна фаза, один план, один цикл Opus-агент-в-worktree — как и весь
сегодняшний UI-проект. Новые функции `remote_control.py`
(`search_packages`, `install_package`) + новая страница
`control_dialog.py::_create_apps_tab`.
